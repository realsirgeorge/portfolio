![Sidedoor — one cleartext POST in a day of TLS](/images/blog/sidedoor-cleartext-cloud-exfiltration/hero.png)

This is a short one, and I like it for that. Not every investigation needs a five-stage exploit chain. Sometimes the answer is "one thing does not look like the others".

The scenario: an insider-threat investigation at a design agency. `capture.pcap` is a full workday of traffic from a monitored workstation. Something left the building that shouldn't have.

## Triage

```console
$ tshark -r capture.pcap -q -z io,phs
```

3,692 frames. Mostly DNS (1,300), TLS (509), ARP, and the usual background. And a great deal of **plain HTTP** — two frames with a `mime_multipart` POST and a JSON response.

On a workstation where everything else is TLS, cleartext HTTP to a "cloud backup" domain is the anomaly. That is the entire detection logic, and it is enough.

```
$ tshark -r capture.pcap -Y http -T fields \
    -e frame.number -e http.request.full_uri -e http.file_data
```

Frame 2846:

```
POST http://sync.cloudbackup-service.net/cloud-sync/upload?session=8f2e1a
```

A multipart form uploading `quarterly_designs_backup.txt` to `185.220.101.47`. Frame 2848 is the server's response:

```json
{"status":"ok","synced":true}
```

![The exfiltration path](/images/blog/sidedoor-cleartext-cloud-exfiltration/flow.png)

## The payload

Decoding the multipart body gives you the file that was uploaded:

```
PROJECT ARCHIVE BACKUP -- INTERNAL USE ONLY
===========================================
This backup was auto-generated by CloudSync Desktop.

recovery-token: r00t{th3_cl0ud_sync_th4t_w4snt}

Do not distribute outside the design team.
```

The flag is riding inside the exfiltrated "backup", which is a nice touch. The attacker exfiltrated the thing that proves the exfiltration.

## Why the disguise works

"Cloud backup" is a favoured exfil costume because:

- It is a normal business activity. Blocking cloud storage outright breaks workflows.
- It uses HTTPS on 443, which blends into the noise.
- The domain can look plausible — `cloudbackup-service.net` is not obviously malicious.
- The upload is small and infrequent, so volume-based detection misses it.

Here, the attacker made one mistake: they used **cleartext HTTP**, not HTTPS. That is what made the traffic visible. In a real incident, the same upload over TLS would have been invisible without TLS inspection or endpoint telemetry, and you would be looking at a JA3 fingerprint and a destination reputation score instead.

## Detection notes

- **Protocol anomaly:** HTTP on a workstation that otherwise speaks TLS. This is a strong, cheap signal.
- **Domain reputation:** newly registered domains, or domains that mimic cloud providers, are worth alerting on.
- **Upload size and direction:** a POST with a file body to an external host, especially outside business hours, is a lead.
- **Multipart bodies:** decode them. Attackers often hide data in a field labelled `backup` or `sync`, and the metadata is as useful as the content.
- **Egress allowlisting:** if the design team only needs a handful of SaaS domains, allowlist them and alert on everything else.

## What I would do differently

Honestly, not much. The challenge is designed to reward `-z io,phs` and one HTTP filter, and that is the correct workflow. If I were writing this up for a client, I would add a timeline: when did the workstation first resolve `sync.cloudbackup-service.net`? What else did it talk to? Is `185.220.101.47` seen anywhere else in the estate?

That last question is the difference between "one user uploaded a file" and "this is a campaign". A single pcap gives you a sample, not a conclusion.
